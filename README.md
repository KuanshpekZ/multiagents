# Многоагентный разбор сетевых инцидентов на IoT-шлюзе

Проект по курсу «Artificial intelligence and machine learning». Тема продолжает магистерскую диссертацию о легковесной системе обнаружения вторжений (IDS) для IoT на основе LightGBM.

Лёгкая модель на шлюзе помечает подозрительные потоки, но выдаёт только вердикт «норма» или «атака». Команда LLM-агентов на сервере превращает поток алертов в разобранные инциденты: что произошло, почему модель так решила, можно ли её обойти и что делать.

**Статус: прототип для Ассайнмента 2.** Работают шлюз и два агента из пяти: Триаж и Объяснение. Они обмениваются структурированными сообщениями и проверены с настоящей языковой моделью (`openai/gpt-oss-120b` через Groq). Остальные три агента спроектированы и описаны в документации.

## Быстрый старт

Нужен Python 3.10 или новее.

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows;  в Linux и macOS: source .venv/bin/activate
pip install -r requirements.txt

python run.py scenarios                          # список сценариев
python run.py run --scenario ddos --llm offline  # проверка без ключа API
```

Чтобы агенты работали с настоящей LLM, нужен ключ любого OpenAI-совместимого API с поддержкой вызова инструментов:

```bash
copy .env.example .env            # Windows;  в Linux и macOS: cp .env.example .env
# впишите LLM_API_KEY в файл .env
python run.py run --scenario ddos
```

В `.env.example` есть готовые настройки для Groq (проверено) и Google Gemini. У бесплатного тарифа Groq для `gpt-oss-120b` лимиты 8 000 токенов в минуту и 200 000 в сутки. Прогон сценария с одним инцидентом тратит около 20–25 тысяч токенов. При превышении минутного лимита клиент сам ждёт и повторяет запрос, поэтому прогон занимает 3–4 минуты. Суточного лимита хватает примерно на 8 прогонов.

### Два режима работы LLM

| Режим | Команда | Что происходит |
| --- | --- | --- |
| `api` | `--llm api` или просто задан ключ в `.env` | Решения принимает языковая модель. Это основной режим для показа. |
| `offline` | `--llm offline` | Вместо LLM работают фиксированные правила из `soc/offline_llm.py`. Сеть не нужна. Это проверка запуска, автотесты и запасной вариант, но не работа языковой модели. |

Цикл агента, инструменты, проверки и журнал в обоих режимах одни и те же.

| Файл | Содержимое |
| --- | --- |
| `report.md` | Отчёт по инцидентам для человека |

Свой файл трафика в формате TON_IoT: `python run.py run --file путь/к/файлу.csv`.

## Данные и модель шлюза

Модель шлюза обучена на сетевой части датасета [TON_IoT](https://research.unsw.edu.au/projects/toniot-datasets) (файл `train_test_network.csv`, 211 043 потока, 9 типов атак) по методике диссертации:

1. Исключены идентификаторы, которые легко подделать: IP-адреса и порты. Также исключены поля с содержимым запросов (DNS-имя, URI, User-Agent, поля сертификата).
2. По важности Random Forest отобраны 11 признаков: `src_pkts`, `src_ip_bytes`, `proto`, `dst_pkts`, `dst_ip_bytes`, `conn_state`, `dns_qclass`, `dns_AA`, `dns_rejected`, `dns_qtype`, `duration`.
3. Обучена лёгкая LightGBM: 50 деревьев глубиной до 5, веса классов, деление 80/20 со стратификацией.

Результат на отложенных 42 209 потоках: точность 99,26%, полнота 99,35%, доля ложных срабатываний 1,06%, размер модели 153 КБ. Все цифры лежат в `models/gateway_meta.json`.

Обученная модель и сценарии уже в репозитории, поэтому система запускается сразу. Чтобы переобучить модель, положите `train_test_network.csv` в `data/raw/` и выполните:

```bash
python scripts/train_gateway.py
python scripts/make_scenarios.py
```

В датасете нет времени потоков. В сценариях время задано искусственно: нормальный трафик идёт равномерно 10 минут, атака идёт плотной серией внутри этого окна.

## Надёжность и безопасность

- **Лимиты.** У агента не больше 8 шагов и 300 секунд, у прогона 900 секунд и не больше 5 инцидентов. На последнем шаге инструменты отключаются, и модель обязана дать ответ.
- **Защита от зацикливания.** Один и тот же вызов инструмента с теми же аргументами выполняется не больше 2 раз.
- **Ошибки инструментов** не роняют агента: текст ошибки возвращается модели, и она может исправиться.
- **Проверка ответа.** Итоговый JSON проверяется по схеме и по смыслу (например, все `group_id` существуют). При ошибке модель получает замечание и до 2 попыток на исправление. Отклонённые ответы записываются в журнал событием `output_rejected`.
- **Сломанный вызов инструмента.** Если модель «вызвала» несуществующий инструмент и провайдер отклонил ответ, агент не падает. Если внутри был итоговый ответ, он проверяется как обычно. Иначе модель получает замечание, и следующий запрос уходит без инструментов.
- **Сбои LLM.** До 4 попыток с паузой; при лимите запросов клиент ждёт столько, сколько просит сервер. Потом выдаётся понятное сообщение.
- **Сбой на одном инциденте** не останавливает разбор остальных.
- **Числа не из LLM.** Количества, вероятности и значения SHAP в сообщениях берутся из инструментов. LLM принимает решения и пишет пояснения.
- **Ключи API** читаются из `.env`, который исключён из git. У агента не может быть больше 5 инструментов: это проверяется в коде.
- **Меры реагирования** в полной версии будут только предлагаться, без автоматического применения.

## Структура проекта

```
run.py                     командная строка
soc/
  config.py                настройки и лимиты из .env
  messages.py              форматы сообщений между агентами (Pydantic)
  agent.py                 базовый цикл агента: лимиты, ошибки, проверка ответа, журнал
  llm.py                   клиент OpenAI-совместимого API с повторами
  offline_llm.py           правила для режима offline
  pipeline.py              конвейер: шлюз -> триаж -> объяснение -> отчёт
  state.py, report.py      состояние прогона и итоговый отчёт
  logging_utils.py         журнал вызовов и подсчёт нагрузки
  gateway/simulator.py     симулятор шлюза с моделью LightGBM
  agents/                  triage.py, explainer.py
  tools/                   triage_tools.py (4 инструмента), xai_tools.py (3 инструмента)
scripts/                   обучение модели, сборка сценариев, рисование схемы
models/                    модель шлюза и её описание
data/scenarios/            тестовые сценарии; data/feature_reference.json — справочник признаков
docs/                      тема, архитектура, спецификация агентов, пример прогона
tests/                     автотесты
explained/                 копия всего кода с построчными пояснениями (для изучения, не для запуска)
```
